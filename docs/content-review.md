# Independent Step 1 content review

Run on October 27, 2026 against commit `0804d72` plus this step's changes.

## What was independent, and what was not

The earlier version of this note said a "separate reviewer" wrote the blind
solutions. The repository could not show that, so that claim is withdrawn.

This review used a fresh agent that did not write the tickets. It received only:

- the user-visible ticket text (title, colleague, instructions, required columns
  with PostgreSQL type OIDs, ordering rule, and any structural requirement);
- the starter query shown in the workspace for each ticket;
- three datasets generated by the repository's own seed generator, with the
  CREATE TABLE and INSERT statements.

It was not given the reference SQL, the wrong variants, the hints, the lessons,
or the source tree. It was told not to open repository files, and it reported
that it did not.

Limit on the result: the fix ticket (`unbilled`) and the window ticket
(`latest-event`) show their starter queries, and the starter already holds most
of the answer. Agreement on those two is weaker evidence than on `dispatch`.

## Pass 1: blind solutions

The agent solved all three tickets and ran each solution on the three datasets
in PGlite 0.5.12 (PostgreSQL 18.6). Its results were then compared with the
repository's reference SQL, executed on the same engine and datasets.

| Ticket | Sample | Nulls | Ties | Column names and OIDs |
| --- | --- | --- | --- | --- |
| dispatch | 5 rows match | 0 rows match | 5 rows match | match |
| unbilled | 8 rows match | 8 rows match | 8 rows match | match |
| latest-event | 218 rows match | 109 rows match | 163 rows match | match |

All 9 combinations matched on rows and column types. The check is reproducible
from the scratchpad, outside the repository.

Ambiguities the agent reported, and how the ticket text now handles them:

- `unbilled`: the starter's `COUNT(*)` counts a LEFT JOIN placeholder row. The
  ticket already says so. The fix is `COUNT(s.id)`.
- `unbilled`: "unbilled" means no invoice references the shipment. Cancelled
  shipments count. The ticket states the rule only by its absence of invoices, so
  this is left as written.
- `latest-event`: the starter omits the event-id tie-breaker. The ticket requires
  it.

## Pass 2: explanations checked against official documentation

A second pass checked every lesson and dialect note against the cited page, and
checked that each cited URL loads. The agent found no incorrect claims. It did
flag claims that the cited page did not support, and link problems. Each flag
was corrected in `src/data/curriculum.ts` or `src/data/challenges.ts`:

- Dialect notes that asserted more than their source supports were rewritten to
  state only what the source documents. These were: Spark LIMIT and ORDER BY
  (chapter 1); T-SQL joins (chapter 4); T-SQL DATEADD (chapter 6); Spark
  CREATE TABLE constraints (chapter 9); T-SQL key integrity and Spark
  star-schema scope (chapter 10); MERGE and Delta wording (chapter 11); T-SQL and
  Spark EXPLAIN (chapter 12); and the Spark interview note (chapter 13).
- The `dispatch` lesson says DESC means largest first. The link list now includes
  the PostgreSQL ORDER BY page, which documents it.
- Chapter PostgreSQL sources were weak or incomplete. Chapter 1 gains the ORDER BY
  and LIMIT pages. Chapter 3 gains the aggregate-functions page, which documents
  COUNT(*) against COUNT(expression). Chapter 4 gains the subquery page, which
  covers NOT EXISTS. Chapter 6 gains the string and date-time function pages.
  Chapter 8 gains the window-function reference. Chapter 9 gains the data-types
  page, and its table-of-contents link is replaced by the constraints page.
- Sentences that were editorial advice rather than documented fact were kept
  only where they say to check the target engine's reference.

The check was done by reading the pages with the agent's fetch tool. It was not
a full reading of each page.

## Wrong-variant detection (per dataset)

Each challenge has one deliberately wrong variant. The matrix records whether
that variant changes the result on each dataset. Measured with the repository's
PGlite runtime on the same datasets:

| Ticket | Sample | Nulls | Ties |
| --- | --- | --- | --- |
| dispatch (`> 500` instead of `>= 500`) | missed | missed | CAUGHT |
| unbilled (`COUNT(*)` instead of `COUNT(s.id)`) | CAUGHT | CAUGHT | CAUGHT |
| latest-event (`id ASC` tie-breaker) | CAUGHT | CAUGHT | CAUGHT |

The `dispatch` boundary bug is caught only by the ties dataset. The visible
sample's five heaviest queued shipments do not include a 500 kg row, and the
nulls dataset has no queued shipments at all. The test suite asserts that each
wrong variant is caught by at least one dataset. It does not assert per-dataset
detection. Changing that requires new edge-case data, which is a decision left
open.
